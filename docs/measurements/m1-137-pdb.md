# M1-137 item 6 — the `.pdb` files of the programs, measured

Status: measured 2026-10-29 on the first machine, in `build/debug`, with clang 23.1.2 and `lld-link`. Register decisions 833, 853
and 864 to 866. The script is
[`m1-137/pdb-measure.py`](m1-137/pdb-measure.py); it only reads the tree.

## The question

In Debug, seven programs read their own `.pdb` file in seven tests, because a
failed assertion prints its chain of calls with the names and lines that the
`.pdb` file gives (decision 833, found by the safety proof of M1-138). The
part of the programs of a test does not hold the `.pdb` file. Item 6 asks if
a change can change a `.pdb` file and keep the bytes of its program.

## The method (decision 853)

A small program of two functions is compiled with the arguments with which
the tree compiles `tests/assertion_message_probe.cpp`, from its
`compile_commands.json`, and linked with the arguments with which the tree
links `assertion_message_probe.exe`, from Ninja: `/Brepro`, `/map`, the
coverage flags and the tree's coverage recorder. It is built four times,
one time after the other in one folder, thus each path stays the same:

| Build | The source |
|---|---|
| base | as it is |
| again | the same again |
| top | a comment line at the top: the lines of the code move |
| end | a comment line at the end: only the text changes |

## The results

| Build | Object | Program | `.pdb` file | Program not as in base |
|---|---|---|---|---|
| again | same | same | same | no byte |
| top | changes | changes | changes | 20 bytes |
| end | changes | changes | changes | 20 bytes |

The 20 bytes are the same in the two builds that change:

- 4 bytes in the headers, at `0x80`: the time stamp of the file;
- 4 and 4 bytes in `.rdata`, at `0xd3df8` and `0xd3e14`: the time stamps of
  the two entries of the debug directory;
- 8 bytes in `.rdata`, at `0xd3e30`: the first half of the identifier of the
  `.pdb` file in the CodeView record. The second half is the text `LLD PDB.`,
  which does not change.

`/Brepro` makes the time stamps and the identifier from a hash, thus the build
gives the same bytes again. No byte of the code changes.

**Thus each change of a `.pdb` file also changes the bytes of its program,
and only in the identifier of the `.pdb` file.**

## What it means for the seven tests

| Test | Takes its program | Examines what the `.pdb` file gives |
|---|---|---|
| `coverage_recorder` | by its bytes, as children | no |
| `assertion_message_precondition` | function by function | yes: the line of the first frame of the chain |
| `assertion_message_postcondition` | function by function | yes: the same |
| `angle_between_zero_aborts` | function by function | no: only that the guard fired |
| `count_wraparound_addition_aborts` | function by function | no |
| `count_wraparound_multiplication_aborts` | function by function | no |
| `count_wraparound_subtraction_aborts` | function by function | no |

A test that takes its program by its bytes has no gap: a change of the `.pdb`
file changes the bytes, and the test runs. A test that takes its program
function by function is skipped when its function part is unchanged, also
when the bytes changed (decision 706), and a change of only the `.pdb` file
changes no function. For the two `assertion_message` tests that is a gap: a
change of only the debug information, for example a compile flag, can make
them fail while the selection skips them. Their test reads the source of the
probe, thus a change of that source runs them.

Each of the six tests took about 2 s in the full run of `889fc03` in Debug.
In RelWithDebInfo the assertions are not live, the probes print `SKIPPED:`,
and no test read a `.pdb` file in the safety proof of M1-138.

## What was done (decisions 864 and 865)

The two `assertion_message` tests take their program by its bytes, through
the list `TAKEN_BY_BYTES` in `scripts/run-tests.py` (decision 844). The rule
applies when a test is recorded and when it is selected, thus an entry that
was stored before the change makes the test run one time. The self-test of
the driver has three cases for it, and each of three planted faults made it
fail, 342 of 343 cases: the rule removed when a test is recorded, the rule
removed when a test is selected, and one test removed from the list.

`run_tests_in_tree` fails when a name in the list is not a test of the tree,
thus a test that is renamed does not leave the list with no failure
(decision 867); a planted name made it fail.

The four other tests stay as they are, because the `.pdb` file cannot change
their result. The limit that stays: a new test that examines the chain of
calls must be added to the list, and the line of item 5 names it.
