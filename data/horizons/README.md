# JPL Horizons reference data

**Nothing in this directory is committed except this file and
`checksums.sha256`.** Everything else is generated by the recipe below and is
gitignored.

That is a licence decision, not a size one — the files are a few kilobytes.
Horizons states no licence anywhere: the
[SSD FAQ](https://ssd.jpl.nasa.gov/faq.html), asked whether you may publish
information from the site, answers *"The short answer is yes"* — permission is
wanted — and asks to be told what you intend to use and how. JPL's reuse policy
grants broad reuse but covers images and video, not data. The API documentation
and the data.gov entry say nothing at all. JPL is a federally funded centre
operated by Caltech rather than a US Government agency, so the exemption that
puts NASA-authored work outside copyright does not apply automatically.

So this project **queries** Horizons, which is plainly fine, and does not
**redistribute** its output. The recipe is committed instead. See
[`../../THIRD_PARTY.md`](../../THIRD_PARTY.md).

## Why there is a conversion step

**A raw Horizons response can never match a committed checksum.** Measured on
2026-09-19: two identical queries five seconds apart differ in line 7, which
stamps the moment of the request —

```
< Ephemeris / API_USER Fri Sep 18 21:42:50 2026 Pasadena, USA      / Horizons
> Ephemeris / API_USER Fri Sep 18 21:42:55 2026 Pasadena, USA      / Horizons
```

— and two more header lines, `EOP file` and `EOP coverage`, change every day as
JPL updates its Earth-orientation data. None of the three affects a geometric,
geocentric state vector; all three change the file's hash.

So each response is turned into this project's own fixture format by
[`../../scripts/horizons-fixture.py`](../../scripts/horizons-fixture.py), which
drops exactly those three lines, keeps the rest of Horizons' header as comments
because it is the provenance, and copies every number **as text, character for
character**. The result is the same bytes whenever the data is the same, and
that was measured too: two fetches of the Sun fixture, at different moments,
gave two different responses and two byte-identical fixtures. The converter
also **refuses** a response in the wrong units, frame or corrections, so a query
that went wrong is found here rather than as a budget that fails for no visible
reason. It does not download anything; fetching is the `curl` below, by hand.

## What is verified without the data

The fixtures' **SHA-256 sums are committed**, in `checksums.sha256` beside this
file. A hash of a file is not that file, so committing it redistributes nothing
— and it turns "I generated a fixture" into "I generated *the same* fixture the
error budgets were measured against". **`check` verifies them**, through the
CTest test `horizons_fixture_checksums`: a fixture with the wrong hash fails,
naming both hashes, and a fixture not yet generated is reported **skipped**, in
CTest's summary, rather than counted as a pass. By hand, either of:

```
sha256sum -c checksums.sha256                                    # from this directory
cmake -DDIRECTORY=data/horizons -P cmake/VerifyFixtureChecksums.cmake   # from the repository root
```

A mismatch means the query drifted or Horizons changed — a new ephemeris, a new
software revision — and either is worth knowing before a budget moves.

## Generating the fixtures

Horizons has a web form and an API. Use the **API**: it is reproducible, and the
query itself is the documentation. Every fixture below is one `curl` and one
conversion.

The parameters, and why each has the value it does:

| Parameter | Value | Why |
|---|---|---|
| `EPHEM_TYPE` | `'VECTORS'` | State vectors, not an observer table |
| `COMMAND` | `'10'` | The Sun |
| `CENTER` | `'500@399'` | The geocentre — Earth's centre of mass, not a site on the surface |
| `REF_PLANE` | `'FRAME'` | The ICRF/J2000 **equatorial** frame, which is what the simulation's inertial frame is. `'ECLIPTIC'` would silently be a different frame |
| `VEC_CORR` | `'NONE'` | **Geometric**, no light-time or aberration. A corrected vector would make the test measure the correction rather than the position — light time to the Sun is about 8 minutes and aberration about 20.5″ |
| `OUT_UNITS` | `'KM-S'` | Kilometres and km/s; the reader converts to metres once, where it can be seen, by moving the decimal exponent rather than multiplying |
| `VEC_TABLE` | `'2'` | Position **and** velocity, no uncertainties |
| `TLIST` | the epochs | Discrete instants rather than a span, so the fixture says exactly which instants it holds. Up to 10,000 |
| `CSV_FORMAT` | `'YES'` | One record per line, which the converter reads |
| `format` | `'text'` | Plain text, not JSON |

### The Sun, geocentric, at forty epochs

**The epochs** (decided 2026-09-19), all at noon TDB so that every Julian date
is a whole number and exact:

- **36 on a 507-day stride from J2000.0**, JD 2451545.0 to 2469290.0, which is
  2000-01-01 to mid-2048. Not a yearly stride: that would put the Sun in almost
  the same direction 36 times. 507 days is 141.75 days more than a year, so each
  epoch lands well round the ecliptic from the last.
- **4 near the apsides**, so that M1-08's distance test has the extremes: the
  perihelion and aphelion of 2000 and of 2050. The days were read from Horizons'
  own geocentric distances, sampled daily at noon — the reference, not the code
  under test — and each extremum fell strictly inside its sampling window:

  | | Noon TDB | JD | Distance |
  |---|---|---|---|
  | Perihelion 2000 | Jan 3 | 2451547.0 | 0.9833216 AU |
  | Aphelion 2000 | Jul 3 | 2451729.0 | 1.0167403 AU |
  | Perihelion 2050 | Jan 4 | 2469811.0 | 0.9833064 AU |
  | Aphelion 2050 | Jul 6 | 2469994.0 | 1.0166282 AU |

From this directory:

```
curl -s --get 'https://ssd.jpl.nasa.gov/api/horizons.api' \
  --data-urlencode "format=text" \
  --data-urlencode "EPHEM_TYPE=VECTORS" \
  --data-urlencode "COMMAND='10'" \
  --data-urlencode "CENTER='500@399'" \
  --data-urlencode "REF_PLANE='FRAME'" \
  --data-urlencode "VEC_CORR='NONE'" \
  --data-urlencode "OUT_UNITS='KM-S'" \
  --data-urlencode "VEC_TABLE='2'" \
  --data-urlencode "CSV_FORMAT='YES'" \
  --data-urlencode "OBJ_DATA='NO'" \
  --data-urlencode "TLIST='2451545.0','2451547.0','2451729.0','2452052.0','2452559.0','2453066.0','2453573.0','2454080.0','2454587.0','2455094.0','2455601.0','2456108.0','2456615.0','2457122.0','2457629.0','2458136.0','2458643.0','2459150.0','2459657.0','2460164.0','2460671.0','2461178.0','2461685.0','2462192.0','2462699.0','2463206.0','2463713.0','2464220.0','2464727.0','2465234.0','2465741.0','2466248.0','2466755.0','2467262.0','2467769.0','2468276.0','2468783.0','2469290.0','2469811.0','2469994.0'" \
  -o sun-geocentric.response.txt

python3 ../../scripts/horizons-fixture.py sun-geocentric.response.txt sun-geocentric.txt
sha256sum -c checksums.sha256
```

**Behind a proxy that cuts off large transfers**, which this response is not —
it is about 12 kB — add `--retry 5 --retry-all-errors -C -` to the `curl`. The
converter refuses a response without a complete `$$SOE` ... `$$EOE` block, so a
truncated download cannot become a fixture unnoticed. Horizons also answers a
malformed query with an error *inside a 200 response*, and the converter
refuses that for the same reason.

## After generating a new fixture

```
sha256sum sun-geocentric.txt >> checksums.sha256   # first time only, then commit it
```

Then `cmake --build build/relwithdebinfo --target check`. The suites that need a
fixture report themselves skipped when it is absent, and say so rather than
passing quietly — a check that silently stops checking is the failure mode
[`../../docs/adr/0005`](../../docs/adr/0005-correctness-is-enforced-by-tools.md)
exists to prevent.
